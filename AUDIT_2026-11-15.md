# NyayaSim audit (15 Nov 2026)

Commit `8c68aee`, branch `nyayasim/foundation`. Read-only: no code was changed.

**How this was checked.** Backend code was read directly: every API router, the schema and
migrations, auth, retrieval, RAG, agent, hearing, ML, backtest split, upload handling and the
citation verifier. The roadmap is `Tab 1.pdf` (6 Nov 2026). Database counts were read from the
running local Postgres. The backend test suite was run earlier today and passed. The landing page
and the example report were viewed in a browser at 1280 px; the other pages were judged from
their code, not seen. Ingestion, the extraction runner, `insights/draft.py` beyond its header,
the benchmark helpers and most test files were skimmed, not read line by line.

## Summary

The engineering is sound and unusually honest about its limits. The grounding design (every quote
checked by code against stored text, a cutoff on every search, money computed in Python) is real
and enforced in code and in database constraints. Three things stand between this and the roadmap:

1. **The product cannot serve a real buyer.** Fact extraction, document answers, the agent and the
   hearing are all blocked for non-demo cases because the only model is the Gemini free tier.
2. **The headline feature has not earned its place.** The stored backtest shows the debate at
   56.5%, a single model call at 58.7% and the claim × delay counting rule at 71.7%. The roadmap
   says a debate that does not beat a single call must be cut or redesigned.
3. **The evaluation rests on unchecked labels.** 502 machine-extracted outcome records, 0 reviewed
   by a person, and the extractor saw the decision pages when it wrote the features.

## 3. RAG pipeline and retrieval configuration

| Setting | Value |
|---|---|
| Chunking | Per page, target 1,000 characters (400 to 1,400), cut at paragraph, sentence, Devanagari stop, line, space. Exact offsets. **No overlap; a chunk never crosses a page.** |
| Embeddings | `BAAI/bge-small-en-v1.5` via fastembed, 384 dimensions, CPU, local. Query prefix set, none on passages. |
| Store | pgvector in Postgres. `order_chunks` (HNSW cosine + GIN) and `case_document_chunks` (separate table, exact scan per case). |
| Keyword side | Postgres `english` full text, query words OR-ed, `ts_rank_cd`. |
| Fusion | Reciprocal rank, k = 60. Pool 60 per list for orders, 40 for a case. |
| Order search | `ef_search` 200 with iterative scan, at most 2 chunks per order, top 10. Cutoff date required and re-checked on every hit. |
| Document answers | Top 6 passages, fixed schema, each quote located in its passage, numbers must match, no surviving citation means "not enough in the documents". |

What is good: the cutoff and the case filter are enforced twice, the public and private indexes
cannot be mixed, and keyword search still works when the embedding model cannot load.

What is weak:

- **No reranker.** The roadmap specifies keyword + vectors + reranker.
- **English only.** The embedding model and the `english` text configuration do nothing useful
  for Hindi, although OCR reads Hindi and the roadmap expects Hindi documents.
- **No relevance threshold.** The plan promised one; today any six passages go to the model.
- **Retrieval quality on orders is unmeasured.** No judged query set exists. The only RAG
  numbers are from 40 questions over four invented documents (recall@5 of 1.0), which the
  project's own notes call small and easy.
- **The hearing's query is a template**, not the case: three or four fixed phrases chosen by
  claim type, plus up to three add-ons. Builder, project and the actual delay are not used.
- A clause that runs over a page break is split and neither half may be retrievable.

## 4. Agent workflow and hearing simulation

**Hearing.** A fixed LangGraph pipeline: buyer advocate, builder advocate, citation gate, judge,
report. One pass each, no rebuttal. Advocates see 12 retrieved chunks labelled P1…Pn and may cite
only those. An argument survives only if every citation verifies. The judge sees survivors only
and its own citations are checked. Outcome shares (Wilson 90% interval, at least 5 labelled
precedents) and the award (calculator at the median precedent rate) are computed by code.

**Agent.** A real plan-act loop: the model picks one of seven tools, `delegate`, or `finish`.
Limits are enforced in code: 6 steps, 3 for a specialist, 7 minutes, identical calls refused,
hearing once, two model failures end the run. Every step is saved as it happens. Final
citations are verified by code whatever the model did.

Findings:

| # | Finding |
|---|---|
| H1 | The debate does not beat a single call (56.5% against 58.7%, McNemar p = 1.0), and both lose to the counting rule (71.7%). On that run the model called 8 of 9 allowed cases "dismissed". A later run with the parties' filings as input reached 67.8% for a single call, still below the rule's 72.9%. |
| H2 | No rebuttal round, although the architecture plan lists one. |
| H3 | The judge's outcome is one label with no probability. The roadmap's calibration target cannot be measured. |
| H4 | Outcome shares need 5 labelled precedents. With 502 labels over 2,209 orders, most hearings will show "insufficient precedent". |
| H5 | The specialist agents were never chosen by the model in live runs; they are tested only with a scripted model. |
| H6 | No agent evaluation exists (`scripts/eval_agent.py` from the plan was not built). |
| H7 | All model calls go to `gemini-3.5-flash-lite` on the free tier, with one fallback. The roadmap asks for a strong judge model and a zero-retention API. |
| H8 | There is no per-run cost or token record, which the roadmap asks for "from day one". |

## 5. Database schema and migrations

17 tables, Alembic head `0010`, all ten migrations applied on the local database.

| Group | Tables |
|---|---|
| Orders | `fetch_log`, `orders`, `order_pages`, `order_chunks`, `case_records` |
| Buyer cases | `cases`, `case_documents`, `case_document_pages`, `case_document_chunks`, `case_questions`, `case_answers`, `facts` |
| Runs | `hearing_runs`, `agent_runs` |
| Accounts | `users`, `user_sessions`, `auth_tokens`, `auth_events` |

Live counts: 13,992 orders listed, 2,209 with text, 72,970 chunks all embedded, 502 outcome
records with 0 reviewed, 4 users, 8 cases, 8 hearing runs, 8 agent runs.

Strengths: CHECK constraints on every enum and range; chunk span must equal text length; a
trigger rejects any fact whose quote is not a substring of its page; partial unique indexes
allow one running hearing and one running agent per case; cascades reach every child of a user.

Gaps:

- `cases.status` has four allowed values and is never updated; the UI derives status itself.
- `cases.updated_at` is never touched after insert.
- No table for statutes or higher-court rulings, which the judge agent is meant to follow.
- No table for human review; `reviewed_by` and `reviewed_at` exist and are empty.
- `orders.source` already allows `up_rera` and `hrera_panchkula`; neither has data.
- Free-text in `auth_events.email` is kept for a year after account deletion (`SET NULL` on the
  user, the email stays).
- No backup job; the roadmap asks for a daily one.

## 6. ML models, training and leakage risks

| Model | Method | Test result | Baseline |
|---|---|---|---|
| Claim type | Relief-section regex rule, else TF-IDF (1 to 2 grams) + logistic regression | 74.3%, macro-F1 0.455, 74 orders | 73.0% majority |
| Outcome | Same model with claim and delay-band tokens appended | 50.8%, macro-F1 0.340, 59 orders | 57.6% majority |
| Outcome rule (served on the report) | Most common outcome by claim type × delay band | 72.9%, 59 orders | — |

The claim-type model beats the majority class by one order in 74. The outcome model is worse than
always guessing the majority, and the API says so. Neither is a result.

The training procedure itself is clean: time split (train before 2024, validation 2024, test from
2025), C chosen on validation, refit on train + validation, one test score, vectoriser fitted
only on training text, and the decision part of each order cut off conservatively.

Leakage and validity risks, most serious first:

| # | Risk | Evidence |
|---|---|---|
| M1 | **Features were extracted with the decision in view.** `claim_type` and `possession_due` in `case_records` come from Gemini reading the first three and last three pages of each order, and the last pages hold the decision and directions. Both then feed the outcome model as tokens and define the counting rule. "Possession due" is often the date the authority itself computed. | `extraction/page_select.py`, `ml/text_classifier.py` `load_items` |
| M2 | **Delay is measured to the decision date.** The delay band uses `decided_on`, and the backtest passes it to the model as the hearing date. A buyer does not know that date; in production the rule uses today instead, so the measured accuracy describes a different input. | `backtest/dataset.py`, `text_classifier._delay_band` |
| M3 | **Training ignores the frozen manifest.** The manifest moves twin orders (same PDF or complaint number) into train. `load_items` and `backtest/dataset.load` assign splits by date alone, so that protection is not applied. | `split_of(o.decided_on)` |
| M4 | **Near-duplicates are not handled.** HRERA issues batches of near-identical orders for one project. Only exact PDF hash and complaint number are compared, so template twins can sit on both sides of the split. | `benchmark/split.py` |
| M5 | **The test set has been reused.** The search query was rewritten after measuring refund cases, the relief rule was added, and several methods were scored on the same 46 to 59 orders. The split is frozen but no longer unseen. | `hearing/inputs.py` comments, MODEL_EVALUATION.md |
| M6 | **Labels are unverified and share a source with the features.** 0 of 502 records are hand-checked; the roadmap requires 200 before trusting the rest. Errors in the label and in the features come from the same model call. | database |
| M7 | **Survivorship.** Orders with no detectable boundary, a short facts part, or outcomes "disposed of" and "withdrawn" are dropped from the evaluation. Those are 87 of the first 248 labels. | `backtest/facts.py`, `OUTCOMES` |
| M8 | **Samples are too small to separate methods.** 59 test orders give a 90% interval of roughly ±10 points. | `MEASURED` |
| M9 | The classifier demo accepts any pasted text. A full order includes its own decision, so the demo is trivially leaky unless the user pastes only the parties' part. | `api/insights.py` |

Not measured at all: award error against real orders, calibration, builder-defence recall,
"citation supports the claim" on a hand sample, OCR error rate, retrieval recall on orders.

## 7. Security and privacy

In place and verified in code:

- Argon2id passwords with rehash, length and common-password rules, equal-time login failure.
- Session tokens of 32 random bytes, stored as SHA-256, HttpOnly, SameSite=Lax, Secure in production.
- Rate limits and lockout on every auth route; one-time email tokens with expiry.
- Origin check on all unsafe methods; strict CSP on the API; CSP and frame denial on the site.
- Case ownership on every case route, answering 404 for another user's case; tests cover it.
- Upload type detected from content, size and page caps, two parallel uploads at most.
- Real documents never go to the model unless a no-retention switch is set; demo cases cannot be
  created on a production server.
- Passages are passed to the model as quoted data and every tool is read-only.
- The API container runs as a non-root user and is bound to localhost behind Caddy.
- No secret in tracked files or in the deploy ZIP.

Missing or weak:

| # | Gap | Roadmap item |
|---|---|---|
| S1 | Uploads and extracted text are stored in plain form on disk and in Postgres. | Encrypted storage |
| S2 | No auto-delete and no per-case or per-document delete. | Auto-delete by default; DPDP deletion |
| S3 | No zero-retention model, so the privacy rule blocks the product for real users. | Zero-retention LLM API |
| S4 | No rate limits outside auth; each `ask`, `agent` or `hearing` call spends model quota and CPU. | — |
| S5 | Rate limiter and job pool live in one process; a second server or a restart resets them. | Redis queue + worker |
| S6 | Website CSP allows `'unsafe-inline'` scripts. | — |
| S7 | `/docs` and `/openapi.json` are public. | — |
| S8 | Trained models are loaded with `joblib` (pickle). Safe only while `data/models` is writable by the app alone. | — |
| S9 | No error alerting, uptime check, backup or CI. | Sentry, uptime, daily backup, backtest in CI |
| S10 | The Gemini key was pasted in chat earlier and should be rotated. | — |
| S11 | Buyer names in public orders are stored and shown as fetched. | Strip buyer names from training records |
| S12 | The privacy page has no grievance contact that I could find. | DPDP grievance contact |
| S13 | Hosting region is undecided; nothing is deployed. | India-region servers |

## 8. Visual design

Verdict: **it reads as a designed product, not a template, on the two pages I saw.** It is not
yet consistent across all pages.

What works:

- A real token system in `globals.css`: one indigo accent, slate neutrals, four status colours
  with soft and border variants, two radii, two shadows.
- Serif headings on the landing page and for legal documents, sans for the interface, mono only
  for order and registration numbers, tabular figures for money.
- The landing page is restrained: one accent, ruled sections, a report excerpt instead of an
  illustration, and a "What it is not" section. No gradients, emoji or stock art.
- The case workspace has a clear header with metadata, a numbered step rail and ledger-style
  tables. Focus rings, a skip link and `aria-current` are present.

What still looks unfinished or generic:

- The palette and component shapes (indigo-700 on slate-50, pill tags, three stat cards on the
  dashboard) are the default look of many dashboards. The serif and the ledger tables are what
  lift it; the dashboard has neither.
- The agent page is raw lists with inline styles and does not match the rest.
- 106 inline styles mean spacing is decided page by page instead of by the system.
- Nine steps in the rail is long, and four of them are closed to a real user.
- The facts page shows extracted text, not the document. The roadmap's PDF viewer with highlights
  is the single most persuasive screen this product could have, and it is missing.
- No dark theme by decision; fine. Mobile layouts exist as `@media` rules but were not viewed.
